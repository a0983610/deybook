## D074 區塊大小可以手動拉（像 VS Code）：左欄寬度、已處理／待處理／輸入區的高度

- **日期**：2026-10-28
- **狀態**：已定案（要做、拉多大就多大、文字模式也要，是使用者說的或選的）；線的樣子、點兩下還原、接著縮下一塊、最小值、怎麼記，是 Claude 定的
- **相關**：D027、D029、D042

> 使用者（附截圖，框起左欄、已處理、待處理、輸入區四塊）：「這些區塊像vscode能夠手動拉 決定佔的大小」
>
> 使用者（Claude 問拉過之後高度怎麼算：「拉多大就多大，點兩下回到跟著內容走」／「拉的是上限，內容少照樣縮到剛好」）：選「拉多大就多大」
>
> 使用者（Claude 問文字模式的兩塊中間也要能拉嗎）：選「要」

**決定**：
- 三條分隔線：左欄｜中間、已處理｜待處理、待處理｜輸入區。平常看起來就是原本的框線，滑過停 0.3 秒、拉的時候亮成 `--accent`；線兩邊各 2px 抓得到。
- 拉的時候線兩邊的區塊互相讓；讓的那邊縮到最小還在拉，就接著縮再過去那塊。
  最小：左欄 150px、已處理／待處理 60px、輸入區 140px（D029 原本的）；左欄最寬到視窗一半。
- **拉多大就多大**：拉過的那塊高度固定，內容少就空著、多就捲動。輸入區不記，永遠是剩下的。
- **點兩下線**回到預設：左欄 180px；線上下那兩塊回到跟著內容走（D029）；文字模式回到各一半。
- 縮起來的那塊（D027）只剩標題列、不分高度：已處理縮起來，已處理｜待處理那條不出現；待處理縮起來，待處理｜輸入區那條不出現，已處理那條改成跟輸入區互相讓。
- 文字模式：只有已處理｜待處理那條（沒有輸入區），拉的是兩塊的比例，跟卡片模式分開記。
- 搜尋、時間軸、標記清單時上下那兩條不出現（兩塊都收起來了）。
- 記在這台電腦：`localStorage` 的 `daybook.sizes`（`side`、`done`、`todo` 是 px，`text` 是已處理佔幾成；沒拉過、點兩下還原是 null）。
  左欄寬度由 `theme.js` 在畫面畫出來前套上，不會先閃一下 180px（同 D042 的縮放）。

**為什麼**：
- 拉多大就多大（使用者選的）：拉的是上限的話，內容少時往下拉線不會動，看起來像壞掉。代價是內容少的日子會空一塊——D029 要避免的就是這個，所以點兩下要能回到跟著內容走。
- 兩個細節是 e2e 量出來的（E54，故意弄壞都會紅）：
  - 拉過的那塊幾乎不縮（`flex: 0 0.001 Npx`）：用一般的 `0 1 Npx`，換到已處理放不下的那天，放不下的部分照 flex-basis 的比例一起縮，
    拉過的待處理從 154px 被縮成 125px。改成 0.001 之後先縮跟著內容走的那塊；全部都拉過、視窗又太小時，才一起照比例縮。
  - 跟著內容走、但放不下在捲動的那塊，按下去時照現在的高度定住：它的高度是「分剩的」，只拉待處理｜輸入區的線往上 30px，
    讓出來的被它拿走（已處理 464 → 494px），輸入區還是 140px，線不跟著游標。放得下的那塊照舊跟著內容走。
- 移不到 3px 不算拉：不然點兩下還原時，第一下手抖就把跟著內容走的那塊變成固定。
- 存 `localStorage`、不經主程序：跟縮起來（D027）、縮放（D042）一樣，只是這台電腦的畫面設定。

**沒採用的做法**：
- 拉的是上限、內容少照樣縮到剛好：使用者沒選，理由見上。
- 只讓線兩邊那兩塊互相讓、不接著縮下一塊：待處理內容少的時候（截圖只有 1 筆），已處理｜待處理那條往下拉沒多遠就卡住（推算，沒實測）。
- 一按就把上下每塊都定住：沒拉到的那塊也不跟著內容走了，跟 D029 衝突太多；只定住非定不可的（拉到的、在捲動的）。

**影響**：
- `index.html` 的 `#sashSide`、`#sashDone`、`#sashTodo`，說明頁「設定與快取」多寫「區塊大小」；
  `style.css` 的 `body`（`--side-w`）、`#days` 的 `position`、`.sash`；`theme.js`；
  `app.js` 的 `sizes`、`applySide`、`stack`、`applySizes`、`sash`、`dragStack`、`resetStack`，`layout`、`togglePane` 最後叫 `applySizes`。
- 之後中間加新的上下區塊，要加進 `stack()`，線也要跟著加。
- 測試 E54。

**實測**（2026-10-28）：parser 331 條、e2e 325 條全過。故意讓拉過的照一般比例縮、拿掉「接著縮下一塊」，E54 各紅 1 條，改回全綠。
用 fixture 複本截圖看過淺色、暗色：沒拉過跟原本一樣、滑過亮一條藍線、拉大的已處理底下空著、待處理在捲動、左欄變寬。
沒測：真的滑鼠（e2e 是 CDP 送的滑鼠事件）、拉的時候游標的樣子、縮放不是 100% 時拉。

**後續**：
- 2026-10-28：外觀頁最上面加「還原預設大小」，一次還原全部拉過的 → 見 D075。

## D077 捲軸照 VS Code：沒箭頭、方形、半透明灰，滑鼠移進那塊才出現；中間那欄 14px、其他 10px

- **日期**：2026-10-28
- **狀態**：已定案（照 VS Code、寬度分兩種、平常藏起來，是使用者說的或選的）；顏色、哪些算「中間那欄」是 Claude 定的
- **相關**：D034、D074

> 使用者（附截圖，框起左欄日期清單、待處理右邊的捲軸）：「拉動條 調整風格 類似vscode的那樣比較粗」
>
> 使用者（Claude 問多寬：照 VS Code 分兩種／全部 14px／全部 10px）：選「照 VS Code 分兩種」
>
> 使用者（Claude 問平常要不要藏起來：一直顯示／跟 VS Code 一樣藏起來）：選「跟 VS Code 一樣藏起來」

**決定**：
- 原本沒設，用的是 Chromium 內建的（細、有上下箭頭）。改成自己畫：沒有箭頭、方形、底是透明的。
- 寬度：`#center` 裡面的（已處理、待處理、輸入區、搜尋結果、文字模式）14px，像 VS Code 的編輯區；其他（左欄、說明這類對話框）10px，像檔案總管。
- 平常看不到，滑鼠移進那塊才出現；滑到捲軸上變深、拉住再深一點。看不到時位置照樣留著，內容不會左右跳。
- 顏色：`--scroll`、`--scroll-hover`、`--scroll-active`，淺色、暗色各一組，值是 VS Code 的 `scrollbarSlider.background`／`hoverBackground`／`activeBackground` 預設色。

**為什麼**：
- 寬度、顏色從本機 VS Code 的程式查的（`resources\app\out\vs\workbench\workbench.desktop.main.js`）：一般捲動區預設 10px（`s3t=10`）、
  編輯區 `verticalScrollbarSize:14`；暗色 `#797979` 40%／`#646464` 70%／`#BFBFBF` 40%，淺色 `#646464` 40%／`#646464` 70%／`#000000` 60%。
  使用者的 VS Code 設定沒改捲軸（只有 `window.zoomLevel: 1`）。
- 要多一條 `:hover { --hovered: 1; }`：只寫 `:hover::-webkit-scrollbar-thumb` 的話，滑鼠移進去 `:hover` 有成立（`matches(':hover')` 是 true），
  捲軸卻不重畫；移到捲軸上、或用 JS 改一下那塊的樣式才畫出來。加一條一般的 `:hover` 對得到那塊，滑過時才會重算、捲軸跟著換。
  量像素確認（暗色側欄底 37）：移進 70、移出 37、滑到捲軸上 81、拉住 98，跟 VS Code 的顏色疊上去算的一樣；拿掉這條 E56 紅。
  一開始以為要用不往下傳的變數（`@property … inherits: false`），不然從待處理移到輸入區時待處理會從 `#center` 繼承到同一個值而不重畫；
  實測拿掉 `@property` E56 照樣全過，所以沒用。

**沒採用的做法**：
- 全部 14px、全部 10px、一直顯示：使用者沒選。
- VS Code 的淡入淡出：沒做，出現、消失是一下子的。捲軸的偽元素應該不吃 `transition`（未驗證）。
- VS Code 捲下去之後頂端的陰影（`scrollbar.shadow`）：不是捲軸本身，使用者沒提。
- `scrollbar-width`／`scrollbar-color`（標準寫法）：寬度只能選 auto／thin／none，定不到 10、14px。

**影響**：
- `style.css` 的 `:root` 三組顏色（淺色、暗色兩段都要有）、「捲軸」那段；`color-scheme: dark` 的註解拿掉「捲軸」（現在自己畫，不跟它變）。

**實測**（2026-10-28）：parser 353 條、e2e 352 條全過。拿掉 `:hover { --hovered: 1; }`，E56 紅 1 條（移進待處理捲軸沒出現），改回全綠。

## D082 記住視窗大小、位置、最大化：關掉時記在設定檔，下次照著開；記的位置看不到就照預設

- **日期**：2026-10-28
- **狀態**：已定案（要記最大化、位置是使用者說的）；關掉時才記、怎樣算看不到、安靜跑不放大是 Claude 定的
- **相關**：D016、D030、D052

> 使用者：「打開始能記憶 視窗開成最大 或位置嗎?」

**決定**：
- 關視窗時（按 ✕、Alt+F4，Electron 的 `close`）把 `getNormalBounds()`（x、y、寬、高）和 `isMaximized()` 記在設定檔的 `window`。
  最大化的也記沒放大時的大小位置：下次開起來放到最大，按「還原」回到那個大小。
- 開視窗時照記的開，記的是最大化就 `maximize()`。沒記過照原本的 1400×860、Windows 決定位置。
- 記的位置看不到就不用，照預設開（最大化照記的）：標題列要有 100px 寬、一半高（標題列抓 30px）露在某個螢幕的工作區裡才算看得到。
- 有 `--data-dir` 時不讀也不寫（D016），開發、e2e 每次都照預設；安靜跑（D052）照記的大小開，但位置照樣在螢幕外、不放大（放大會回到螢幕上）。
- 寫設定檔失敗不丟錯：不能擋住關視窗。

**為什麼**：
- 只在關掉時記：設定檔的其他東西（資料夾、擴充、外觀包）也是有變才寫；拖動、拉大小時一直寫沒必要。
  代價是當掉、被強制結束那次的大小位置不會記到，下次照再上一次的開。
- 「看得到」要看標題列，不是整個視窗都在螢幕內：視窗拖一半到螢幕外、貼齊左右邊（Windows 會把看不到的邊框算進去，x 可能是 -7 這種，未驗證）都是正常用法，
  整個視窗都要在螢幕裡的話這些都會被打回預設。只要標題列抓得到，就拖得回來。
- 判斷寫成純函式 `window-state.js` 的 `restore`：要測螢幕拔掉、貼邊這些情況，e2e 做不出來，parser 測試直接給螢幕工作區就能測（W1）。

**沒採用的做法**：
- 拖動、拉大小時就記（`move`、`resize` 停手再寫）：當掉也記得到，但多一套計時、一直寫檔；使用者沒要求。
- 記的位置看不到時，把視窗拉回最近的螢幕：要算縮放、邊界，照預設開就看得到了。
- 記的大小比現在的螢幕大時縮小：沒做；標題列看得到就拖得動、拉得小（比螢幕大時 Windows 實際怎麼開，未驗證）。
- 裝現成的套件（例如 `electron-window-state`）：要裝新套件（CLAUDE.md 要先問），自己寫只有一個函式。

**影響**：
- 新檔 `src/main/window-state.js`；`main.js` 的 `createWindow`（讀 `readSettings().window`、`screen.getAllDisplays()` 的 `workArea`，`close` 時寫）。
- 設定檔多一個 key `window: { x, y, width, height, maximized }`，跟 `dataDir`、`extensions`、`skin` 放一起，寫的時候其他 key 照留。
- 之後要改預設大小，改 `createWindow` 的 1400、860；`--quiet-window` 的螢幕外位置要放在 `...last.bounds` 後面才蓋得過。
- 測試 W1（parser）、E59（e2e）。

**實測**（2026-10-28）：parser 411 條、e2e 380 條全過。故意讓 `restore` 不看螢幕（數字對就用）W1 紅 5 條；
拿掉 `...last.bounds`、拿掉 `close` 時記，E59 各紅 1 條；改回全綠。
E59 用 Windows 的關視窗（`CloseMainWindow`，送 WM_CLOSE，跟按 ✕ 一樣）關，才走得到 `close`；測試平常的 `browser.close()` 加 kill 不會走到。
沒測：真的視窗開在記的位置、開起來是最大化（安靜跑在螢幕外、不能放大，要完整跑或使用者自己開才看得到）；最大化時先閃一下原本大小才放大會不會看得出來；
縮到工作列時關掉（從工作列右鍵關）記的是什麼；螢幕縮放不是 100%、兩個螢幕縮放不一樣。

> 使用者（Claude 問卡片上顯示：顯示符號、標顏色，編輯時預覽／直接顯示填好的樣子）：選「顯示符號、標顏色」

**決定**：
- 內文裡的 `{…}` 是日期符號：複製時換成那一刻的日期時間，檔案裡存的照寫的（`[{yyyy.MM.dd HH:mm} cm8]`）。
- 認的符號照 C# 的日期格式（大小寫有分）：`yyyy` 年、`yy` 年兩碼、`MM` 月、`M` 月不補零、`dd` 日、`d` 日不補零、`HH` 時（24 小時）、`H` 時不補零、`mm` 分、`ss` 秒。
- 怎樣算符號：大括號在同一行、裡面的英文字母整段都是上面的符號（同一個字母連在一起算一個，`MMM` 就不認）、至少有一個；
  其他字（標點、空白、中文、數字）照原樣，所以 `{yyyy年M月d日}` 也行。裡面有別的英文字、或一個符號都沒有的照原樣：`{0}`、`{ get; set; }`、`{hh:mm}`、`{}`。
- 卡片上照寫的顯示，符號那段（含大括號）用強調色；新增、編輯時內文有符號，底下即時預覽「複製時：…」。內文的提示字寫了這種寫法。

**為什麼**：
- 寫法、顯示：使用者選的。符號照 C#：使用者是 C# 開發者，`MM`／`mm` 的大小寫跟平常寫的一樣。
- 「整段都要是符號才算」：暫存很可能放程式碼片段，`string.Format("{0}")`、`{ get; set; }` 這種大括號不能被動到；只認大括號、不加前綴（像 `{now:…}`）是使用者選的短寫法，用這條規則擋掉撞到的情況。
  擋不掉的是剛好整段都是符號的，例如程式碼裡的 `{d}`、`{M}`——會被換成日、月（未遇過，記著）。
- 換字放在畫面（`src/renderer/datefill.js`），不放主程序：編輯時的預覽要即時算，畫面拿不到 `src/shared` 的 CommonJS；照 `cutout.js` 的寫法，畫面用 `<script>` 載入、測試用 `require`。
  複製時畫面先換好再交給 `snip:copy`，主程序照舊只轉換行（D093）。
- 時間用 `new Date()`（這台電腦的時區），跟畫面上的「今天」一樣是本機時間。

**沒採用的做法**：
- `{now:yyyy.MM.dd HH:mm}`、固定的 `{日期}` `{時間}`、卡片直接顯示填好的樣子：使用者沒選。
- 星期（`ddd`）、12 小時制（`hh`、`tt`）、只寫一碼的分秒（`m`、`s`）：使用者的例子用不到，先不認；要加在 `DATE_TOKENS` 加一行。
- 跳脫寫法（讓整段都是符號的大括號照原樣）：還沒遇到要的情況。
